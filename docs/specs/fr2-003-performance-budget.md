# 功能规格：PixiJS 高密度渲染与后端索引性能预算

> 状态：开发中　·　关联 PRD：FR2-003 / FR2-005 / FR2-007 / FR2-009　·　阶段：P0 `0.21.x`　·　分支：未指定

## 1. 背景与目标

v2 明确要求首个 mock UI 就验证 100 万以上素材的前端渲染性能，同时后端数据库索引要提前按 500 万到 1000 万媒体资产设计。旧时间轴的性能问题不能再靠 DOM 虚拟列表局部修补解决，核心滚动热区必须从一开始按 PixiJS 渲染路径设计。

目标：

- 把 PixiJS 定为高密度媒体网格/时间轴滚动热区的默认方案。
- 明确 100 万素材前端 mock UI 的渲染、纹理、缩略图和 HLS 预览预算。
- 明确 100 万、500 万、1000 万资产后端索引、分页、筛选、排序和任务队列压测口径。
- 明确 React DOM 壳层与 PixiJS 的边界，避免核心滚动热区回到重 DOM。

## 2. 数据集口径

| 数据集 | 用途 | 规模 | 内容组成 |
|---|---|---|---|
| `media-ui-smoke-100k` | 日常快速回归 | 10 万媒体 | 视频为主，图片少量混入，覆盖 Space、时间、路径、状态、缩略图、HLS 预览占位 |
| `media-ui-target-1m` | 首个 mock UI 和 P3 默认验收 | 100 万媒体 | 多 Space、多年份、多目录层级、视频时长、转码状态、AI 状态、缩略图/HLS 预览状态 |
| `media-index-5m` | 后端索引目标 | 500 万媒体 | 覆盖路径、时间、类型、任务状态、AI 状态、Space 权限过滤 |
| `media-index-10m` | 后端索引压力边界 | 1000 万媒体 | 极端目录、极端单日、跨 Space、任务高水位、索引重建和分页游标压力 |

Mock 数据必须确定性生成：同一 seed 生成相同媒体 ID、Space、路径、日期、时长、状态、AI 标记和缩略图/HLS 状态，便于性能报告可复现。

## 3. 前端 PixiJS 性能预算

| 指标 | `1m` 目标 | 超限处理 |
|---|---|---|
| 初始可交互 | 3s 内进入可滚动状态，不等待全量数据或纹理加载 | 区分数据拉取、Pixi 初始化、纹理首批加载和 React 壳层耗时 |
| 连续滚动帧耗时 | p95 ≤ 16.7ms，p99 ≤ 33ms | 先优化 Pixi 容器层级、纹理池、可见窗口和批处理 |
| 长任务 | 10s 滚动窗口内无 >200ms 主线程长任务 | 拆分计算、降低同步纹理上传、移动重计算到 worker 或后端 |
| Pixi display objects | 只保留可视区 + overscan 所需对象，不随 100 万数据线性增长 | 检查对象池复用和销毁策略 |
| GPU/纹理内存 | 有纹理池上限；快速滚动不无限缓存缩略图 | 纹理 LRU、降级占位、释放不可见纹理 |
| 缩略图请求 | 只请求可视区 + overscan；过期请求可取消或丢弃结果 | 禁止快速滚动排队全量缩略图 |
| HLS 预览入口 | hover/选中时才请求轻量预览元数据或片段，不在滚动时自动播放大量视频 | 视频预览与滚动解耦，预览层独立限流 |
| React 重渲染 | 滚动时 React 壳层不随每帧重渲染 | Pixi 状态与 React 控制态分层 |

## 4. 后端索引性能预算

| 指标 | `5m` 目标 | `10m` 压力门槛 | 超限处理 |
|---|---|---|---|
| Space + 时间分页 | 常用页查询 p95 ≤ 200ms | p95 ≤ 500ms 且可解释 | 调整组合索引、游标分页或物化视图 |
| Space + 路径前缀 | p95 ≤ 300ms | p95 ≤ 800ms | 检查路径规范化、前缀索引和目录表 |
| 筛选组合 | 类型/状态/时间/Space 组合 p95 ≤ 300ms | p95 ≤ 800ms | 追加组合索引或拆查询 |
| 任务队列查询 | 待转码/待 AI/失败重试查询 p95 ≤ 100ms | p95 ≤ 300ms | 任务状态索引和批量领取策略 |
| 批量入库 | 批量写入不阻塞读查询；有明确批大小 | 大批导入期间 UI 仍可分页浏览 | 批处理、事务边界、后台队列 |
| 索引重建 | 可按 Space/库/时间范围分片重建 | 全量重建有进度和可恢复状态 | 不允许无进度长事务 |

P0/P1 先定义索引口径和 benchmark harness；实际数据库、FTS、向量索引或扩展选择必须由压测结果和 ADR 决定。

## 5. 前后端协同策略

- 前端不持有 100 万完整对象数组，只持有可见窗口、索引游标、轻量缓存和选中状态。
- 筛选、排序、Space 权限和 AI 状态过滤必须优先在后端索引层完成。
- PixiJS 只渲染当前窗口和必要 overscan；详情、任务、审核和表单由 React 组件显示。
- HLS 预览不能与滚动抢主线程和网络；预览请求必须限流并可取消。
- 缩略图、HLS 代理、向量索引和 AI 中间结果都是可重建数据，Benchmark 可清缓存后复测。

## 6. Benchmark 输出

每次 Benchmark 至少输出：

- 前端：浏览器、GPU、屏幕尺寸、设备像素比、构建模式、数据集、seed。
- 前端：初始化耗时、滚动帧耗时分位数、长任务、JS heap、Pixi 对象数、纹理数量、纹理内存估计、缩略图/HLS 请求数量。
- 后端：数据库大小、索引列表、数据规模、查询 SQL/参数、耗时分位数、扫描行数、写入批大小、任务队列水位。
- 操作脚本：首屏加载、连续滚动、快速跳时间、Space 切换、筛选、HLS 预览、任务队列过滤。

报告产物进入 `.tmp/` 或 CI artifact，不直接进入仓库；稳定预算和结论进入对应 spec / ADR。

## 7. 验收标准

- P1 mockup/UI 博物馆必须能展示 PixiJS 100 万素材渲染样例。
- P1/P2 后端 benchmark 必须覆盖 100 万、500 万、1000 万资产索引查询。
- P3 高密度媒体浏览器必须附 `media-ui-target-1m` Benchmark 结果。
- 如果 SQLite 或现有索引策略无法满足 500 万到 1000 万资产目标，必须写 ADR 决定索引/数据库替代方案。
- 性能失败项必须能映射到 FR2、spec 或 ADR，不能只写“页面很卡”。

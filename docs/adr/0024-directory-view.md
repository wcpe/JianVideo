# ADR-0024：文件目录视图架构决策

## 状态
已接受

## 背景
用户需要以传统文件资源管理器风格浏览媒体库中的视频文件（FR-15）。现有系统仅提供按添加时间排序的时间轴视图。需要提供按目录层级浏览、面包屑导航、文件列表展示的能力。本 FR 属于二期，无依赖。

## 决策
采用「SQLite file_path 前缀聚合 + Go 层 map 分组」方案实现目录浏览 API，前端采用「Tab 切换（时间轴 | 文件目录）+ 面包屑导航 + 文件列表」的经典文件管理器布局。

## 理由
- 复用现有 `media_files` 表，通过 `file_path` LIKE 前缀查询一次获取所有匹配文件，Go 层按第一级子目录分组，避免新增数据库表
- 面包屑由后端构建，前端直接渲染，减少前端路径处理逻辑
- Tab 切换集成到现有 LibraryPage，不新增独立页面，保持导航简洁
- 侧边栏目录树懒加载延后到 V2，降低一期实现复杂度
- 为 `file_path` 添加索引，加速前缀查询，确保 NFR-08 500ms 响应时间要求

## 后果
- 新增 `GET /api/library/browse` 端点，扩展了 API 契约
- 新增 `BrowseResponse`、`DirInfo`、`BreadcrumbItem` 数据模型
- LibraryPage 从单一时间轴视图扩展为 Tab 双视图
- `file_path` 索引增加写入开销，但大幅提升目录浏览查询性能

## 备选方案
- **纯 SQL 分组**：用 SQL 的 SUBSTR/REPLACE 提取第一级子目录并在数据库层分组。落选原因：不同数据库的字符串函数差异大，SQLite 的字符串处理不如 Go 灵活
- **文件系统实时扫描**：每次请求都用 `os.ReadDir` 扫描文件系统获取子目录。落选原因：文件系统 I/O 比数据库查询慢，且无法直接获取已索引的媒体文件元数据
- **维护目录树表**：新增 `directories` 表维护完整的目录结构。落选原因：增加数据模型复杂度，目录变更需要同步维护

# ADR-0021：播放末端缓冲等待策略

## 状态
已接受

## 背景
播放追播场景下，当播放器读取速度追上文件写入速度时，会遇到文件末端。此时如果不做处理，可能触发 mpegts.js 的 Network Error 导致播放器崩溃，或者 HTTP Range 请求返回 416 Requested Range Not Satisfiable。需要一种机制来优雅地处理这种"追上写入末端"的情况。

## 决策
采用"前端缓冲等待 + 后端追播等待"的双端协作策略：
- 前端检测到达文件末端时进入缓冲等待状态，显示 UI 提示，定时轮询检测新数据
- 后端 HLS 写入器在追播模式下，读取到文件末尾时阻塞等待新数据而非立即返回错误
- 前端监听 mpegts.js ERROR 事件，自动延迟 1 秒重试播放

## 理由
- **前端控制体验**：缓冲等待 UI 和恢复逻辑在前端实现，用户看到的是统一的等待提示而非浏览器默认的加载动画
- **后端保证数据可用性**：追播等待确保 HTTP Range 请求不会因文件位置越界而失败，减少不必要的错误传播
- **简单可靠**：轮询 m3u8 索引文件是最简单的"新数据检测"方案，不依赖 WebSocket 或 SSE 等复杂推送机制
- **错误重试兜底**：自动重试机制确保偶发的网络波动不会导致播放中断

## 后果
- 前端需要维护额外的状态机（playing/buffering/error）
- 后端 HLS 写入器需要支持阻塞等待，增加了 HTTP 处理器的复杂度
- 轮询间隔（2 秒）和重试延迟（1 秒）是硬编码值，后续可配置化

## 备选方案
- **WebSocket 推送通知**：后端通过 WebSocket 通知前端有新数据。实时性更好，但增加了后端复杂度和前端依赖。当前场景下轮询 m3u8 已足够。
- **原生 video 标签 stalled 事件**：利用浏览器原生播放器的缓冲事件。但 mpegts.js 直接操作 MSE，不走原生播放管线，此方案不可行。
- **HTTP 206 Partial Content 持续返回**：后端对 Range 请求持续返回 206 直到新数据可用。实现简单但可能导致连接过长，增加服务器资源占用。

# ADR-0037：目录浏览聚合多库（单一虚拟根逐库下钻）

## 状态
提议中

## 背景

目录浏览（FR-15 / FR-33，[ADR](（无单独 ADR，见 ARCHITECTURE §5.0）)）此前是**单库视图**：`GET /api/library/browse` 必须带 `library_id`，前端 `BrowsePage` 写死取第一个库根目录（`paths[0]`）作为浏览起点，且用一次性 `initialized` ref 锁住，只初始化一次。

后果：注册了 ≥2 个存储库时，目录浏览页**只能看到第一个库**，无法切换到其他库；新增库后页面也不刷新（锁已置位）。需要一个能同时进入所有库、逐库下钻的浏览入口。

需要决策：多库如何统一进入、浏览模型怎么扩展、是否新增端点。

## 决策

**目录浏览顶层聚合所有启用存储库为单一「虚拟根」，点击某库下钻进入该库现有单库浏览树。**

- **虚拟根标记**：`GET /api/library/browse` 的 `parent_path` 取哨兵值 `__root__` 时进入**聚合根分支**，忽略 `library_id`，返回所有启用（`enabled=1`）存储库作为顶层「目录」项；其余 `parent_path` 走原单库逻辑（必须带有效 `library_id`），分支外行为字节级不变。
- **目录项携库 ID**：聚合根返回的目录项需让前端知道点进去用哪个 `library_id`，故 `DirInfo` 增加可选字段 `library_id`（仅聚合根项填充，普通子目录项不填、`omitempty` 不出现）。`name`=库 `label`（缺省回退 `path`），`path`=库注册 `path`。
- **根面包屑**：聚合根返回单段面包屑 `[{name:"全部存储库", path:"__root__"}]`，下钻进库后面包屑首段为虚拟根、可点回。
- **前端去写死与去锁**：`BrowsePage` 不再取 `paths[0]`，无库定位查询参数时以虚拟根 `__root__` 初始化；`useDirectoryBrowse` 去掉 `initialized` 一次性锁，改由「是否带显式库定位」驱动，根层点库下钻时记住该 `library_id`、回到根时清空。新增库即时反映（根列表实时由后端聚合返回）。

## 理由

- **为何复用 `browse` 端点加聚合分支，而非新增 `browse-root` 端点**：浏览是同一语义连续体（根 → 库 → 子目录），前端用同一套 `useDirectoryBrowse` 状态机下钻最简；新增端点会让前端分叉两套加载/面包屑逻辑。哨兵 `parent_path` 分支是最小侵入，原单库路径零改动。
- **为何用 `__root__` 哨兵而非空 `parent_path`**：原端点空 `parent_path` 已定义为 400（不能为空），语义被占用；显式哨兵不与任何真实路径冲突（真实路径不含该串），且前端面包屑可直接以它作根节点 path。
- **为何 `DirInfo` 加 `library_id` 而非另造类型**：根项与子目录项在前端是同一份目录列表、同一套渲染与「进入目录」交互，复用 `DirInfo` 只差一个「进入时切到哪个库」的信息，加一个 `omitempty` 字段比并行第二种类型更内聚（避免贫血并行模型）。
- **为何只列启用库**：禁用库不参与浏览与扫描语义一致；`library_paths.enabled` 已是真源。
- **真源不变**：库列表真源仍是 `library_paths` 表，媒体真源仍是 `media_files` 表；聚合根只是换一种读取视图，不新增持久状态。

## 后果

- **正**：多库可在同一页逐库浏览、自由切换；新增库即时出现在根；单库下钻路径与现有 FR-33 浏览体验完全一致（零回归）。
- **正**：后端单测可覆盖「聚合根返回所有启用库 / 单库下钻分支不变 / 禁用库不列」。
- **边界**：聚合根不递归列各库内文件，仅列库本身作顶层目录（点进去才查该库内容），与「逐库下钻」语义一致、避免一次扫全部库。
- **依赖方向**：聚合分支在 `library.Service`，端点在 `api` 包，方向不变（`web → media-library → db`），无反向依赖。
- **契约兼容**：`DirInfo.library_id` 为新增可选字段，旧响应（普通子目录）不含它，前端旧消费者忽略未知字段；`browse` 端点对带 `library_id` + 真实 `parent_path` 的旧请求行为不变（向后兼容）。
- 与 ARCHITECTURE §5.0：在其「单库 browse」描述之上**扩展**聚合根浏览模型，不取代单库下钻。

## 备选方案

- **新增 `GET /api/library/browse-root` 端点**：前端要维护两套加载与面包屑逻辑，下钻时还要在两端点间切换，复杂度更高。否。
- **前端纯前端聚合（不动后端）**：前端拿 `paths` 自己拼根列表可行，但面包屑「回到根」「下钻库」状态仍需后端无关的特例分支，且与后端浏览契约割裂；后端出聚合根让前后端共用一套下钻模型更内聚。否（但前端仍需去写死与去锁，二者不冲突）。
- **空 `parent_path` 表示根**：与原端点「parent_path 不能为空 → 400」语义冲突，改动面更大且易误触发。否。

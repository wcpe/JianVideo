# ADR-0056：采用 Space 归属与角色权限的多用户数据模型

## 状态
已接受

## 背景

[ADR-0053](0053-video-ai-pixijs-space-baseline.md) 把 Space 确立为 v2 的唯一策略边界：权限、删除、同步、AI 可见性、分享、审计和写回都必须按 Space 执行，不做全局模糊权限。但 ADR-0053 只给出定位，没有定落库形态。本 ADR 是它的落实层，回答“Space 与多用户在 SQLite 里怎么建表、权限在哪一层校验”。

约束与现状：

- 现状是 [ADR-0016](0016-single-user-auth.md) 的单用户 Cookie + JWT 认证，业务资源没有归属维度，必须向后兼容。
- 单实例按 10 到 50 用户、500 万到 1000 万资产设计（ADR-0053）。
- 完整的角色、成员管理、分享增强、家长控制、回收站在 P5（`0.26.x`）才落地，而资源表结构在 P2（`0.23.x`）存储库与索引落地时就要冻结。
- 若 P5 才给资源表加归属字段，会触发已有百万级数据的整库迁移与返工。

## 决策

采用“最小归属先行、完整权限后置”两步走。

**P2 最小归属（`0.23.x`）**：

1. 新增 `spaces` 表：`id`、`name`、`created_at` 等基础字段。
2. 所有业务资源表（`media_files`、`library_paths`、转码/AI 任务、AI 结果、分享记录等）新增 `space_id` 外键，非空、建索引，作为行级隔离维度。
3. 首次初始化（承接 ADR-0040 引导）建“默认 Space”，把现有单用户设为其 owner；历史资源全部归入默认 Space。迁移路径与验证挂 [ADR-0060](0060-v2-migration-plan.md)。
4. 数据经数据层抽象持久化（[ADR-0058](0058-data-layer-abstraction.md)），业务层不直接拼 SQL。

**P5 完整权限（`0.26.x`）**：

5. 新增 `space_members(user_id, space_id, role)`，表达“用户在某 Space 的角色”，联合唯一。
6. 角色枚举取最小集：`owner`（空间与成员管理、删除恢复、全部读写、分享）、`editor`（增删改查、写回、发起任务）、`viewer`（只读浏览与播放）。
7. 权限矩阵：

   | 能力 | owner | editor | viewer |
   |---|---|---|---|
   | 浏览 / 播放（查） | 是 | 是 | 是 |
   | 新增 / 修改 / 写回（增改） | 是 | 是 | 否 |
   | 删除 / 恢复 | 是 | 是 | 否 |
   | 分享 | 是 | 是 | 否 |
   | AI 结果可见 | 是 | 是 | 是 |
   | 成员与角色管理 | 是 | 否 | 否 |

8. 权限校验统一在服务层做行级过滤：所有列表、详情、写操作强制带当前用户可访问的 `space_id` 集合作为过滤条件，越权访问在数据到达前被过滤，不依赖前端隐藏。
9. 审计按 Space：事件日志、任务（挂 [ADR-0055](0055-task-queue-persistence.md)）都带 `space_id`，可按 Space 追溯与回滚。
10. 分享默认只读，且分享链接的访问也按 Space 与资源归属校验；匿名分享不触发转码、AI 等高成本任务（呼应 FR2-010 的匿名分享防高成本口径）。

## 理由

- Space 归属字段是 P2 与 P5 之间的跨阶段接缝，schema 只有一次定对的机会；P2 先把 `space_id` 挂上，P5 只加成员与角色表、补校验，避免整库迁移。
- 默认单一 Space + owner 能让现状单用户在无感知情况下平滑进入多用户模型，满足对 ADR-0016 的向后兼容。
- 行级过滤在服务层集中做，能防止“各资源各写一套可见性规则”，也把越权挡在数据层之前，符合 ADR-0053“不跨 Space 隐式泄露”。
- 角色取 owner/editor/viewer 最小集，覆盖 10 到 50 用户的家庭/小团队场景，不引入过度的细粒度 RBAC。
- 分享只读且按 Space 校验、匿名不触发高成本任务，避免分享成为绕过权限或放大资源消耗的入口。

## 后果

- 这是 P2（最小归属）与 P5（完整权限）跨阶段的接缝，`space_id` 的 schema 必须在 P2 一次定对；后续若要改归属维度需另写取代 ADR。
- P2 阶段虽只有默认 Space，也必须写全 `space_id` 并建索引，不得留空或延后。
- 服务层所有查询都要带 Space 过滤，成为固定审查项；遗漏即越权风险，需在测试高风险区专门覆盖。
- 分享、家长控制（FR2-051）、回收站保留期（FR2-054）等 P5 能力都在本模型上叠加，不再自建归属或可见性规则。
- 迁移（[ADR-0060](0060-v2-migration-plan.md)）必须保证历史资源无遗漏地归入默认 Space，且可验证、可回滚。

## 备选方案

- **全局模糊权限、不引入 Space 归属**：实现最省，但被 ADR-0053 明确禁止，会导致权限、分享、AI 可见性各做一套。
- **P5 才引入 `space_id`**：P2 结构更简单，但等百万级数据落地后再加归属列会触发整库迁移与大面积返工。
- **引入外部权限系统或完整 RBAC 框架**：能力更强，但对 10 到 50 用户的自托管单实例过重，违背简单优先与一体化部署目标。
- **把角色权限直接硬编码在各业务处理器里**：短期快，但校验散落、易漏、无法统一审计，等同放弃单一策略边界。

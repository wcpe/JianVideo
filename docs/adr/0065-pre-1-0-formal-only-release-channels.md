# ADR-0065：1.0.0 前仅正式版；1.0.0 起才启用 RC/GA 渠道

## 状态
已接受（补充 [ADR-0064](0064-gated-rc-ga-release.md)；不取代其门禁与构建机制）

## 背景

ADR-0064 建立了 `dev` 实验工件、推 tag 门控的公开 RC（`vX.Y.Z-rc.N`）与稳定 GA（`vX.Y.Z`）发布路径，以及自更新「稳定 / 候选版 RC」双频道。机制本身可用，但产品在 `0.y.z` 预稳定阶段若也按「每 minor 先 RC 再 GA」叙事，会带来：

1. 与「v2 在 1.0.0 前持续迭代、每阶段直接交付可用正式版」的路线图语义冲突（例如 `0.25.0`、`0.26.0` 已是对用户可用的阶段正式发布，不是候选）。
2. 自更新与文档中「候选版 RC」与「阶段正式版」混用，用户难以判断 `0.x` 是否可安心升级。
3. P3 历史曾出现 `v0.24.0-rc.1` 等 `0.x` 候选 tag，属于当时实践；后续若继续在 `0.26`/`0.27` 等线推 `0.y.z-rc.N`，会放大口径漂移。

因此需要在不改动 ADR-0064 工程门禁的前提下，明确**何时允许使用 RC/GA 渠道标签**。

## 决策

1. **`1.0.0` 之前（所有 `0.y.z`）一律只发正式版**  
   - 公开 GitHub Release 仅使用稳定 tag：`v0.Y.Z`（`VERSION=0.Y.Z`），走 `release.yml` 正式发布路径，`prerelease=false`、可标 latest（相对当时最新正式 tag）。  
   - **禁止**为 `0.y.z` 新建 `v0.Y.Z-rc.N` 公开候选 Release，也**禁止**在 PRD/验收/CHANGELOG/对外文案中把某次 `0.x` 发布称为「RC 候选」或「GA」。  
   - `dev` 仍只产出短期 Actions 实验工件（ADR-0064 §2），不进入自更新。

2. **自 `1.0.0` 起才引入 RC 与 GA 区分**  
   - 首个稳定目标：先推 `v1.0.0-rc.N`（`rc.yml`，prerelease、非 latest），验收通过后再推 `v1.0.0`（`release.yml`，stable/latest）。  
   - `1.x` / `2.x` 等后续 major/minor 可继续使用 `X.Y.Z-rc.N` → `X.Y.Z` 门控路径；严格 SemVer 从 `1.0.0` 起执行（见 `docs/ROADMAP.md`）。

3. **路线图阶段名与渠道标签解耦**  
   - 分期表中的「P8 `0.29.x`（1.0 候选准备）」表示**功能冻结与 1.0 候选准备阶段**（版本线仍是正式 `0.29.x` patch），**不是**「发布 `0.29.0-rc.N`」。  
   - 真正的公开 RC 从准备并推送 `1.0.0-rc.1` 开始；「GA」专指 `1.0.0` 及之后的稳定正式 tag。

4. **历史兼容**  
   - 已存在的 `0.x` 候选 tag/Release（如历史 `v0.24.0-rc.1`）可保留查询；自更新与文档不再鼓励新产生同类 `0.x` RC。  
   - ADR-0064 的工作流、四门、双平台构建、draft 回验、自更新比较规则保持有效；本 ADR 只约束**产品策略与何时推 RC tag**。

## 理由

- 预稳定阶段需要频繁、可升级的正式阶段交付，而不是每条 minor 再套一层 RC 仪式。  
- 把「候选信任等级」留给真正的 1.0 冻结窗口，避免 `0.x` 用户被「候选/正式」双重叙事干扰。  
- 与现有 `release.yml`（稳定 tag）能力对齐：1.0 前只走稳定正式路径即可，无需改流水线代码即可落地策略。

## 后果

- 正面：`0.21.x`–`0.29.x` 阶段发布口径统一为正式版；1.0 起 RC/GA 语义清晰。  
- 约束：发 `0.26.0` 等版本时准备 `VERSION`/`CHANGELOG` 稳定段并推 `v0.Y.Z`，不写 `0.26.0-rc.N`。  
- 文档：ROADMAP / CONTRIBUTING / PRD / ARCHITECTURE / FR2-014 规格须写明本策略；验收报告不得把 P5 等阶段出口写成「进 0.x RC」。  
- 兼容：ADR-0064 机制保留；P8 阶段名可继续称「1.0 候选准备」，公开 tag 仍用正式 `0.29.x` 直至 `1.0.0-rc.N`。

## 备选方案

- **0.x 也强制 RC→GA**：与当前阶段正式交付习惯冲突，增加无收益仪式，落选。  
- **取消 RC 工作流直至 1.0 再引入**：机制已存在且 1.0 需要，保留流水线、仅约束使用时机更省事，落选「删掉 rc.yml」。  
- **用 beta/alpha 代替 0.x 正式版**：增加频道复杂度且与「阶段正式可用」目标不符，落选。

# ADR-0055：通用任务队列中心采用 SQLite 持久化与进程内 worker 池

## 状态
已接受

## 背景

v2 需要承载大量异步任务：转码、缩略图、预览生成、元数据回写、图片导出、视频剪辑导出，以及 P6 的 AI 推理（见 [ADR-0059](0059-ai-pipeline-vector-index.md) AI 管线）。这些任务大多耗时、可失败、需断点续跑，并且要在进程重启后不丢。

当前代码里已存在两套局部队列，形态高度一致：

- library 扫描队列（FR-29）：以 SQLite `scan_tasks` 表为持久化真源，单 worker 串行执行，重启把残留 `running` 重置为 `pending` 重新入队。
- transcoder 预生成队列（FR-77）：以 SQLite `transcode_tasks` 表为持久化真源，单 worker 串行执行，重启同样恢复残留任务。

两者已各自实现「持久化 + 单 worker 串行 + 重启恢复」，但表结构、调度、恢复逻辑各写一套，语义相近却不复用。v2 若继续让每个新任务类型（缩略图、导出、AI 推理等）各建一张表、各起一个 worker，会造成重复实现与运维口径不统一（无法在一处看全所有任务、无法统一限流与重试）。

架构不变量 §2 明确禁止 Redis、RabbitMQ 等外部消息队列或缓存中间件；§0 说明 v2 任务队列默认按进程内或 SQLite 持久化设计，除非新 ADR 明确批准外部中间件。本 ADR 不批准任何外部中间件。

## 决策

v2 建立一个**通用任务队列中心**，采用 **SQLite 持久化 + 进程内 worker 池调度**，统一承载全部异步任务；**不引入 Redis/RabbitMQ 等外部消息队列**。它泛化并收敛现有 FR-29 扫描队列与 FR-77 预生成队列。

任务表（经数据层抽象 [ADR-0058](0058-data-layer-abstraction.md) 持久化）核心字段：

| 字段 | 说明 |
|---|---|
| 任务类型 | 转码 / 缩略图 / 预览 / 元数据回写 / 图片导出 / 剪辑导出 / AI 推理等，决定所属并发池 |
| 状态 | `pending` / `running` / `succeeded` / `failed` / `canceled` |
| 优先级 | 数值优先级，供调度排序 |
| 重试次数 | 已重试次数，配合退避策略 |
| 断点 / 进度 | 已完成进度与断点位置，供恢复与展示 |
| Space 归属 | 关联 [ADR-0056](0056-space-permission-model.md) Space，任务隔离与配额的归属维度 |
| 负载（payload） | 任务参数（如 media_id、编码、导出配置），按类型自定义 |
| 错误信息 | 失败时的错误摘要 |
| 创建 / 更新时间 | 入队与最近状态变更时刻 |

状态机：`pending → running → succeeded / failed / canceled`；`failed` 在未超重试上限时按退避重新入队回到 `pending`。

调度模型：

- **优先级 + 公平**：先按优先级、再按入队时间取任务，避免高优先级饿死低优先级。
- **按任务类型分并发池**：不同类型有各自的 worker 池，池并发上限可配（如转码池小、缩略图池大）。
- **worker 池为后台 goroutine**，从入队到执行全程异步，**不阻塞 web 请求线程**；入队接口立即返回任务 ID。
- **幂等 / 断点 / 重启恢复**：进程重启时把残留 `running` 任务按类型语义恢复（重排回 `pending`）或从断点续跑；重复入队按幂等键去重，不重复执行。

队列监控查询接口：提供按类型、状态、Space 过滤的任务列表与统计查询，供任务队列中心页（FR2-037）展示与操作（取消、重试）。

定位：该队列中心是 P2 地基，实现在迁移后的 `apps/server`；被 AI 管线（[ADR-0059](0059-ai-pipeline-vector-index.md)）、迁移（[ADR-0060](0060-v2-migration-plan.md)）等后续能力复用，不为其各自另起队列。

## 理由

- 现有两套局部队列已验证「SQLite 持久化 + 单 worker + 重启恢复」在自托管单机形态下够用且可靠，泛化为通用队列是自然演进，风险可控。
- SQLite 已是元数据唯一真源，任务落同一库便于事务一致、无需额外中间件与运维成本，契合简单优先与架构不变量。
- 进程内 worker 池足以满足单机自托管的并发需求，避免分布式消息队列的部署、故障域与一致性复杂度。
- 按类型分池 + 可配并发上限，能针对转码（重）与缩略图（轻）等差异化限流，避免某类任务占满资源。
- 统一一处入队、调度、监控，消除各模块各写一套队列的重复，也让 FR2-037 有单一数据来源。

## 后果

- FR-29 扫描队列与 FR-77 预生成队列收敛为通用队列中心的两种任务类型；两者现有「持久化 + 单 worker + 重启恢复」语义被通用模型覆盖，不再各自维护独立表与调度逻辑（迁移落地另走实现 spec）。
- 任务持久化经数据层抽象（[ADR-0058](0058-data-layer-abstraction.md)）完成，队列中心不直接写 SQL；任务表与元数据表同库同事务边界。
- 任务与 Space（[ADR-0056](0056-space-permission-model.md)）绑定，为后续多用户隔离与配额留出归属维度。
- 后续 AI 管线（[ADR-0059](0059-ai-pipeline-vector-index.md)）与迁移（[ADR-0060](0060-v2-migration-plan.md)）复用本队列，不新建平行队列。
- 关联 PRD FR2-037（通用任务队列中心）与 FR2-023/033/038/039。
- 当前 `docs/ARCHITECTURE.md` 在代码迁移完成前仍描述现状（FR-29/FR-77 两套局部队列）；通用队列中心以本 ADR、PRD 与 specs 为准，迁移完成后再同步 ARCHITECTURE。

## 备选方案

- **引入外部消息队列（Redis/RabbitMQ）**：具备成熟的重试、优先级、可观测能力，但违背架构不变量 §2/§0（禁外部中间件）与简单优先原则，给自托管单机形态强加部署与运维负担，被否。
- **纯内存队列**：实现最简、无落库开销，但进程重启即丢未完成任务，无法满足断点续跑与重启恢复，被否。
- **继续各模块各自维护局部队列**：贴近现状、改动小，但每新增任务类型都要重复一套表 + worker + 恢复逻辑，无法统一监控、限流与重试，且与 FR2-037 单一任务中心目标相悖，被否。

# ADR-0026：自适应码率（ABR）实现决策

## 状态
已接受

## 背景
当前系统仅支持单码率 HLS 输出。需要在网络波动时自动切换码率以保证流畅播放。面临两个核心决策：如何生成多码率流，以及如何在客户端实现自适应切换。

## 决策
采用 FFmpeg filter_complex split 单进程多输出方式生成多码率 HLS 切片，配合 hls.js 实现客户端自适应码率切换。

## 理由
- **单进程多输出 vs 多进程**：filter_complex split 确保所有码率共享同一 GOP 边界，避免多路独立转码导致的 GOP 不对齐问题。单进程也减少资源开销。
- **hls.js vs 原生 video 标签**：原生 video 标签不支持动态追加 TS 流（追播模式），hls.js 基于 MSE API 同时支持 ABR 和追播。
- **动态 import**：hls.js 仅在 ABR 模式下加载，不增加不使用 ABR 场景的 bundle 体积。
- **码率阶梯自动裁剪**：源分辨率不足时不生成更高码率，避免无意义的上采样。

## 后果
- 转码资源消耗增加（单进程但多路编码），需要硬件加速支持
- 前端增加 hls.js 依赖（约 200KB gzip）
- 切片文件命名需要包含码率维度，与现有单码率逻辑不兼容（需改造）

## 备选方案
- **多进程独立转码**：每个码率启动独立 ffmpeg 进程。落选原因：GOP 不对齐，资源开销大。
- **使用 DASH 协议替代 HLS**：落选原因：mpegts.js 不支持 DASH，且 HLS 在浏览器端支持更广。
- **原生 video 标签 + HLS**：落选原因：原生 video 不支持动态追播（边下边播场景会中断）。

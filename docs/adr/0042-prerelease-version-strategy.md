# ADR-0042：预发布版本号策略与同基线更新判定语义

## 状态
已接受（扩展 [ADR-0032](0032-release-engineering.md) 的预发布/自更新决策）

## 背景
ADR-0032 确立了「正式发布（tag 触发）+ 滚动 dev 预发布（push main 触发）+ 二进制自更新」体系。
其预发布版本号策略（FIX-3）取 `max(最新正式版 tag, VERSION 文件)` 的**下一修订号**作 dev 基线，
本意是避免「dev < 已发布正式版」的倒挂。但该策略有两处缺陷，导致测试版频道「一直有更新」：

1. **dev 版本号凭空高一位**：发布正式版后（如 0.17.1），dev 基线恒为 `0.17.2-dev.<SHA>`——
   即便主干自该正式版起**无任何新提交**，发布正式版这一动作本身就制造了一个「更高的 dev」，
   测试版用户被误导为有更新。
2. **后端同基线判定按短 SHA 比较**：`hasUpdate` 对同基线两个预发布返回 `latest.pre != current.pre`，
   只要短 SHA 变了（每次 push main 重建 dev）即判「有更新」，造成 churn 误报。

## 决策
1. **dev 版本号反映真实主干进度**：dev 版本号格式改为 `<基线>-dev.<提交距离>.g<短SHA>`，其中
   - 基线 = 最新正式版 tag 的版本号本身（**不再 +1 修订号**）；
   - 提交距离 = 自该 tag 起的提交数（`git rev-list --count <tag>..HEAD`），随主干新增实质提交单调递增。
   语义版本上 `<基线>-dev.*` 介于「已发布的 `<基线>`」与「下个正式版」之间，既不倒挂、又不凭空高一位。
2. **提交距离为 0 时不发布 dev**：HEAD 正是正式版 tag 所指提交（主干无新提交）时，
   `scripts/dev-version.sh` 退出码非 0、不输出版本号，`prerelease.yml` 据此跳过 build/prerelease，
   避免「发完正式版后无新提交仍滚动出更高 dev」。
3. **同基线更新判定按「提交距离序号」而非短 SHA**：`hasUpdate` 在同基线预发布判定中，
   双方均为 `dev.<序号>.g<sha>` 时仅当 `latest 序号 > current 序号` 才提示更新——
   主干无新提交、仅短 SHA 改写时序号不变即不误报；当前为同基线正式版时仍可切到 dev。
   旧格式 dev（无 `dev.N.` 前缀）退回「标识不同即更新」的保守兜底，保持向后兼容。

## 理由
- 「提交距离」是「主干是否真有新提交」的可靠、单调信号，比「短 SHA 是否变化」精确，
  从根上消除「发正式版即假更新」与「push churn 误报」两类问题。
- 基线不再 +1，使 dev 版本号语义诚实地表达「这是 `<基线>` 之后、下个正式版之前的开发预览」。
- 推导逻辑收敛到 `scripts/dev-version.sh`（带 `scripts/dev-version_test.sh`），CI 与本地一致；
  后端判定收敛到纯函数（`devSeq` + 同基线子判定），可穷举单测。

## 后果
- 正面：测试版频道仅在主干有新实质提交时提示更新；装上最新 dev 再检查不提示；
  发完正式版且无新提交时不提示 dev 更新。三条验收（FIX-1）由单测 + 脚本测试覆盖。
- 约束：dev 版本号格式变更（`-dev.<SHA>` → `-dev.<提交距离>.g<SHA>`），
  已装旧格式 dev 的用户首次比较走保守兜底（标识不同即提示一次更新到新格式 dev），属一次性可接受过渡。
- 真机验收门控：真实发布/打 tag/GitHub Release 链路本机无法跑，端到端「发版后频道不再误报」留作真机验。

## 备选方案
- **基线继续 +1、仅改后端判定**：dev 版本号仍凭空高一位，语义不诚实，且「发版即假更新」无法根治，落选。
- **后端继续按短 SHA 比较、仅靠 CI 跳过空提交**：force-push/amend 等历史改写仍会让序号相同而 SHA 变化，
  按短 SHA 比较仍误报；按序号比较更稳健，落选纯 CI 方案。
- **dev 用时间戳作序号**：时间戳不反映「是否有新提交」（重跑 CI 时间也变），不如提交距离精确，落选。

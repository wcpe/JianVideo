# ADR-0003：HLS/TS 强制输出作为转码格式

## 状态
已接受

## 背景
转码输出需要选择一种流媒体格式。候选方案包括 HLS（m3u8+TS）、DASH（MPD+fragment MP4）、直接 MP4 流式传输、WebRTC。需要权衡浏览器兼容性、网络适应性、追播能力和实现复杂度。

## 决策
转码输出固定采用 HLS（m3u8 + TS 切片）格式，强制输出。

## 理由
- **浏览器兼容性**：HLS 在 Safari 原生支持，Chrome/Firefox 通过 mpegts.js 支持，覆盖面最广。
- **追播能力**：TS 切片天然支持实时追加，mpegts.js 可通过 HTTP Range 请求获取最新切片数据，实现"边下边播"和"实时追随"。
- **网络适应性**：HLS 设计之初就考虑了网络波动场景，支持多码率阶梯切换（ABR）。
- **HTTP Range 友好**：TS 切片是独立文件，天然支持 HTTP Range 请求，便于 Seek 操作。
- **实现简单**：FFmpeg 的 `hls` muxer 成熟可靠，配合 `-f mpegts` 可直接输出裸流。

## 后果
- TS 切片相比 MP4 容器开销略大（约 2-5% 的存储冗余）。
- 需要管理切片文件的清理（转码会话结束后或定时清理过期切片）。
- mpegts.js 是前端唯一选择（原生 video 标签无法播放 TS 流）。

## 备选方案
- **DASH + fragment MP4**：标准化程度高，但在浏览器端需要 dash.js，追播能力不如 mpegts.js 成熟。
- **直接 MP4 流式传输**：Seek 依赖 `moov` atom 位置，需要等待元数据写入完成才能拖拽，体验差。
- **WebRTC**：超低延迟但实现复杂，服务器资源消耗大，不适合本地网络场景。

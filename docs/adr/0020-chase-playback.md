# ADR-0020：追播模式下的 HLS 切片管理与前端追播控制

## 状态
已接受

## 背景
FR-17 需要实现"边下边播"与实时追随。FR-06 确定了 HLS/TS 强制输出格式，FR-08 实现了流式输出，FR-16 引入了 mpegts.js 播放内核。现在需要解决两个问题：(1) 后端如何在追播模式下持续写入切片而不标记结束；(2) 前端如何利用 mpegts.js 的追播能力自动追加新数据。

## 决策
1. 后端引入 `HLSManager` 封装切片写入逻辑，追播模式下永不写入 `EXT-X-ENDLIST`。
2. 前端 VideoPlayer 组件通过 mpegts.js 的 `isLive: true` + `stashInitialSize` 配置控制追播延迟在 3-5 秒。
3. 追播模式通过 URL 查询参数 `?live=true` 切换，无需新增 API 端点。

## 理由
- **HLSManager 封装**：将切片写入、m3u8 索引管理封装为独立模块，职责单一，便于测试和维护。
- **mpegts.js 原生追播**：mpegts.js 内置 `isLive` 模式和缓冲区管理，无需自行实现轮询逻辑，减少复杂度。
- **stashInitialSize 控制延迟**：通过调整初始缓冲区大小，可以精确控制追播延迟（2MB ≈ 3-5 秒@典型码率）。
- **查询参数切换**：复用现有 `/api/play/stream` 端点，最小化 API 变更。

## 后果
- 后端需要管理切片文件的写入和索引更新，增加文件系统操作。
- 追播模式下 m3u8 文件会持续增长，需要后续版本引入切片清理策略。
- 前端 VideoPlayer 组件依赖 mpegts.js，如果未来更换播放内核需要重写该组件。

## 备选方案
- **前端轮询 + 手动追加**：不依赖 mpegts.js 的 isLive 模式，前端定时轮询 m3u8 并手动通过 MSE API 追加数据。实现复杂且容易出错，不采用。
- **WebSocket 推送**：后端通过 WebSocket 推送新切片信息。实时性更好但增加了后端复杂度，且 mpegts.js 已支持追播无需额外机制，不采用。
- **完整 HLS 会话管理**：引入完整的 HLS 会话生命周期管理（创建、续期、销毁）。功能完整但超出 FR-17 范围，留待后续版本。

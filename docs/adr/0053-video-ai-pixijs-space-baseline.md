# ADR-0053：采用视频优先、Space 边界、AI 可替换与 PixiJS 高密度渲染基线

## 状态
已接受

## 背景

v2 最新要求已经超出“轻量单用户家庭媒体库”的边界：目标变为自托管优先的视频素材与 AI 媒体中心。核心要求包括：

- 1.0 核心路径不依赖官方云账号、官方中继、官方托管存储或官方 SaaS 多租户。
- 原文件安全优先，删除、写回、迁移和同步必须可追溯、可恢复或明确提示风险。
- AI 是核心能力，但模型、索引、推理节点和重建策略不能绑死。
- Space 是权限、删除、同步、AI 可见性、分享、审计和写回的策略边界。
- 缩略图、代理文件、索引和 AI 中间结果是可重建数据，原媒体、sidecar、事件日志和人工元数据是可信源。
- 单实例按 500 万到 1000 万媒体资产、10 到 50 用户的重度素材库基线设计。
- 首个 mock UI 即要求验证 100 万以上素材的前端渲染性能，并要求后端索引性能同步压测。
- 产品主线以视频媒体、HLS 预览、转码任务队列和 AI 高级能力为主，不再以相册和上传为核心。

## 决策

从 `v0.21.0` 起，JianVideo v2 的架构基线调整为：

1. 产品定位改为“自托管视频素材与 AI 媒体中心”，不再按单用户轻量相册产品设计。
2. 核心浏览渲染采用 PixiJS-first 策略：PixiJS 承载 100 万级媒体网格/时间轴滚动热区，React DOM 壳层只承载壳层、面板、表单、弹窗、wiki UI 博物馆和非热区组件。
3. 入库以存储库扫描为主，Web 上传从 1.0 主线移除。后续如恢复上传，必须按 Space、路径安全、审计和原文件安全重新立项。
4. Space 成为策略边界：权限、删除、同步、AI 可见性、分享、审计和写回必须关联 Space。
5. 数据分为可信源与可重建数据：原媒体、sidecar、事件日志、人工元数据是可信源；缩略图、HLS 代理、索引、向量、AI 中间结果必须能删除并重建。
6. AI 管线必须可替换、可审计：模型、索引、推理节点、任务队列和重建策略都不能成为不可替换黑盒。
7. 后端索引从 P0/P1 开始按 100 万、500 万、1000 万资产压测，不等 UI 完成后再补性能。
8. 端形态覆盖 Web、Desktop、Android、iOS、Android TV 和安卓车机，但一体化部署优先，默认不要求用户维护多服务集群。

## 理由

- 100 万级前端滚动和 1000 万级后端索引不是普通 DOM 卡片堆叠能可靠承载的，应从第一版 mock UI 就用 PixiJS 验证渲染路径。
- 用户明确要求视频媒体为主，转码、任务队列、HLS 预览和 AI 能力优先，继续围绕相册/上传组织路线会错位。
- Space 作为唯一策略边界能防止权限、分享、AI 可见性和删除恢复各自做一套规则。
- AI 结果天然可能误判，必须把可信源和可重建数据分开，人工元数据和事件日志优先。
- 自托管优先要求 1.0 核心路径不能依赖官方云或官方 SaaS，否则会偏离部署目标。

## 后果

- `docs/PRD.md` 和 `docs/ROADMAP.md` 必须从“轻量家庭媒体中心”调整为“视频素材与 AI 媒体中心”。
- `docs/specs/fr2-003-performance-budget.md` 必须把 PixiJS、100 万 UI mock、500 万到 1000 万后端索引压测列为前置口径。
- `docs/specs/fr2-004-compatibility-matrix.md` 必须把旧相册、上传、照片娱乐流等能力从 1.0 主线中降级或移出。
- `docs/ARCHITECTURE.md` 在代码实际迁移前仍描述当前真貌；目标架构由本 ADR、PRD 和 specs 承载。
- 引入 PixiJS、移动端壳、AI 模型运行时、向量索引或数据库扩展时，仍需在具体实现前单独确认依赖与规格。
- SQLite 是否足以承载 500 万到 1000 万资产与 10 到 50 用户，需要 Benchmark 证据；若不达标，必须另写 ADR 决定索引/数据库替代方案。

## 备选方案

- **继续轻量单用户家庭媒体库路线**：改动少，但无法满足 1000 万资产、多用户、Space、AI 和多端要求。
- **React DOM 虚拟滚动路线**：实现简单，但 100 万级高密度缩略图/视频预览滚动风险高，且之前已暴露体验瓶颈。
- **直接上完整云端多租户架构**：可扩展性强，但违背自托管优先和一体化部署目标。
- **AI 绑定单一模型/向量库**：短期快，但不可审计、不可替换，后续迁移成本高。

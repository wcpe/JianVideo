# ADR-0036：端到端编码协商（播放发起时选实际编码与播放路径）


## 状态
提议中

## 背景

FR-49（[ADR-0033](0033-hwaccel-probe-source-cache.md)）以实测为真源给出「系统可产出编码并集」；FR-50（[ADR-0034](0034-configurable-target-codec.md)）持久化「首选目标编码优先级」；FR-51（[ADR-0035](0035-fmp4-mse-playback-path.md)）按目标编码产出 fMP4/CMAF 或 TS 两条路径；FR-52 在前端探测「客户端可解码哪些高级编码」并提供按描述符分发的自适应播放器。四块各自就位，但**谁来决定「这次播放实际用哪个编码、走哪条路径」尚无归属**：

- 首选优先级是「想要」，客户端能力是「能播」，硬件可产出是「能造」，三者求交才是「实际能用」。
- 缺一个统一的协商点，前端无从知道某媒体该请求 TS 还是 fMP4、该用什么 MIME 初始化 MSE。

需要决策：协商在哪做、用什么契约暴露给前端、产出与会话如何接线。

## 决策

**在播放发起时做一次服务端协商，经新增端点把结果以「播放描述符」契约下发前端。**

- **协商算法（纯函数）**：`ChosenCodec(priority, clientCaps, producible)` = 首选优先级里第一个同时满足「客户端支持」且「实测可产出」的编码；都不满足兜底 `h264`。`h264` 为恒可用底座（现有 mpegts.js+TS 路径保证可播）。
- **协商端点**：`POST /api/play/:id/negotiate`，请求体携带客户端能力 `{h265,av1,vp9}`（来自 FR-52 探测）。后端读 FR-50 优先级 + FR-49 可产出并集 + 客户端能力 → 协商实际编码。
- **按协商实际产出**：`h264` → 现有 TS 路径（master.m3u8 / stream，分支不动）；非 `h264` → 调 FR-51 `PreSliceWithCodec` 产 fMP4，产出失败则**降级回 h264**（不报错，保证可播）。
- **返回播放描述符**：`{codec, path(ts/fmp4), url(清单), mime, fallbackUrl}`，前端交 FR-52 自适应播放器分发。
- **会话记录实际编码与路径**：把协商结果记到内存播放会话（`PlaybackSession` 新增 `target_codec`/`output_path` 两字段）。

## 理由

- **为何在服务端协商**：「可产出」只有服务端知道（实测真源在后端），「优先级」也在后端持久化；客户端只持有「能播」一项。把三者求交放后端、一次性下发，前端最薄。
- **为何用新端点而非扩展现有发起逻辑**：现有播放发起是前端直接探测 `master.m3u8`（GET），无「上报客户端能力」的入口。协商必须接收客户端能力，新增 `POST .../negotiate` 是最贴合的接入点，且 H.264 路径维持原 master 探测行为不变（向后兼容）。
- **为何 `h264` 兜底而非报错**：H.264/TS 是验收过的恒可用路径；任何协商不出高级编码（客户端不支持、不可产出、优先级为空、fMP4 产出失败）都回落它，保证「总能播」。
- **为何产出失败降级而非 500**：fMP4 产出是外部 ffmpeg，可能失败；降级 h264 让用户仍能播（虽非首选编码），优于直接报错。
- **为何会话只记内存不新建表**：现有 `PlaybackSession` 即内存会话（FR-12 Range 跟踪），协商结果附着其上改动最小。ARCHITECTURE 历史上描述过 `transcode_sessions` 持久表但代码从未落地；本 FR 不新建该表，避免镀金。

## 后果

- **正**：四个 FR 端到端串通，高级编码在支持的浏览器可实际播放；H.264 路径与追播零回归。
- **正**：协商纯函数可穷举单测；端点契约清晰，前端只消费描述符。
- **负 / 边界**：negotiate 同步产 fMP4，长视频耗时较长（沿用 FR-51 的 10 分钟硬上限）；异步产出 + 轮询属后续优化。
- **负 / 边界**：会话记录不持久化，进程重启丢失（与现状一致）。
- **硬件维度待硬件**：软件 AV1 端到端可真机验；硬件 AV1/QSV/NVENC 端到端待对应硬件。
- **依赖方向**：协商纯函数在 `transcoder` 包，端点在 `api` 包经 `library/settings/transcoder/playback` 协调，方向不变（`web → media-library/transcoder → db`），无反向依赖。
- 与 [ADR-0034](0034-configurable-target-codec.md)/[ADR-0035](0035-fmp4-mse-playback-path.md)：**复用不取代**，本 ADR 在其之上新增「协商点 + 端点契约」。

## 备选方案

- **客户端自行协商**：客户端拿不到「可产出并集」与「优先级」，无法独立决策。否。
- **扩展现有 `master.m3u8` 探测做协商**：GET 探测无法携带客户端能力上报，且会污染已验收的 H.264 探测路径。否。
- **新建持久化 `transcode_sessions` 表记协商**：当前会话本就只在内存、无持久化需求，新建表属镀金（范围纪律）。否。
- **协商不出高级编码就报错**：违背「总能播」，H.264 兜底更稳。否。

# ADR-0061：运行期设置采用类型化注册表与分层边界

## 状态
已接受

## 背景

ADR-0029 已接受“运行期设置持久化采用 SQLite settings 表”，当时的目标是用简单 key/value 表承载少量单用户业务配置。P2 会继续加入任务队列、缓存、工具下载、转码偏好、媒体类型规则、硬件加速、代理与审计接入点。如果继续允许任意 key 批量 upsert，配置项会缺少类型、默认值、敏感性、热应用能力和消费模块边界，旧客户端或测试也可能写入拼写错误的脏 key。

本决策取代 ADR-0029 的“任意 key upsert”部分；SQLite `settings` 表作为运行期设置真源的判断不变。

## 决策

运行期设置继续存放在 SQLite `settings` 表，但所有可写 key 必须先登记到类型化注册表。注册表是运行期设置的唯一契约，包含 key、中文名称、分层、值类型、默认值、校验函数、敏感标记、是否允许热应用、消费模块与应用钩子。

配置按两个维度描述：

- 分层：`startup`、`runtime`、`readonly`。只有 `runtime` key 可以通过 `PUT /api/settings` 写入。
- 敏感性：`Sensitive` 独立标记，不与分层混用。敏感值允许写入和存在性展示，但不得明文回显、进日志或进审计事件。

兼容策略：

- `GET /api/settings` 保持旧 map 形态，返回已登记 key 的当前值或默认值；敏感值只返回脱敏状态。
- `PUT /api/settings` 写未知 key 返回 `400`，且批量写整体失败，不产生新脏 key。
- 旧数据库中已经存在但未登记的 key 不删除；迁移与诊断接口报告它们，业务代码不得继续依赖未登记 key。
- 新增 `GET /api/settings/definitions` 暴露配置定义，供前端渲染分组、控件类型和校验提示。

应用语义：

- 保存前先执行注册表 `Validate`，全部通过后在一个事务里写入 settings。
- 事务提交后执行对应 `Apply` 钩子。热应用失败必须返回中文错误并记录审计/日志，响应中不得宣称已热应用。
- `HotApply=false` 的 key 保存后返回“需重启”提示，不假装即时生效。

安全边界：

- 本决策不新增 settings 落库加密体系；敏感项先通过不回显、脱敏审计、日志脱敏与权限边界控制风险。
- 若未来要求敏感 settings 静态加密，需要另写 ADR 定密钥来源、轮换、备份恢复与迁移策略。

## 理由

- SQLite settings 表仍然符合单机自托管与简单优先，不需要引入配置中心。
- 类型化注册表能把 key、类型、默认值、校验、敏感性和消费模块集中到一处，避免魔法字符串散落。
- 未知 key 直接失败比“写入但没人消费”更容易暴露错误，能防止配置漂移继续扩大。
- 保留旧 map 读写端点能兼容现有前端与客户端；新增 definitions 接口只补足元数据。
- 敏感值静态加密牵涉密钥生命周期，当前没有明确密钥管理方案，先不把半成品加密体系写进地基。

## 后果

- ADR-0029 中“新增设置项只需新增 key 常量”的部分被注册表流程替代；新增可写配置必须先登记定义并补测试。
- 旧客户端向 `/api/settings` 写未知 key 会从静默成功变为 `400`，这是有意收紧的兼容边界。
- 前端设置页可以从 definitions 渲染控件，减少前后端配置定义双写。
- 各业务模块需要提供清晰的 Validate/Apply 钩子，热应用能力必须可测试。
- FR2-024 按本 ADR 落地配置注册表、未知 key 拒绝和敏感项脱敏策略。

## 备选方案

- **继续任意 key upsert**：改动最少，但配置漂移无法收敛，敏感性与热应用语义无法统一，被否。
- **把所有配置迁到启动配置文件**：能集中配置，但运行期修改、事务一致和前端保存会退化，违背现有 settings 真源，被否。
- **引入外部配置中心**：能力完整，但违反单机自托管与无外部中间件边界，被否。
- **立刻引入 settings 加密**：安全收益明确，但密钥来源、轮换、备份恢复和旧值迁移未定，超出当前地基范围，被否。

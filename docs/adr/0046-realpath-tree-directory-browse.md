# ADR-0046：目录浏览聚合改为真实路径树（取代 ADR-0037）

## 状态

已接受（取代 [ADR-0037](0037-aggregate-directory-browse.md)）

## 背景

[ADR-0037](0037-aggregate-directory-browse.md)（FR-66）把目录浏览的聚合定为「**虚拟库根**」——顶层并列列出各启用媒体库、靠 `library_id` 逐库下钻。该模型有一个用户实际遇到的缺口：**看不出库之间的真实路径包含关系**。例如同时添加 `D:\1` 与 `D:\1\2` 两个库，界面显示成两个并排的顶层库，无法呈现 `2` 是 `1` 的子目录；也无法「从盘符根整体浏览」（加 `D:\` 库时按真实路径下钻）。

用户明确要求目录浏览像 Windows 资源管理器：**把所有添加的媒体库按真实磁盘路径合并成一棵大目录树**，盘符/共享为根，传 `D:\` 即整盘可浏览。这与 ADR-0037 的虚拟库根模型相悖，需写新 ADR 取代。

## 决策

目录浏览聚合由「虚拟库根 + library_id 逐库下钻」改为「**真实磁盘路径树 + 跨库前缀聚合**」：

- 顶层 = 各启用库路径推导出的**卷根/共享根**（`D:`、`//host/share` 等）去重。
- 浏览任意真实路径 P 时，**不依赖 library_id**：子目录 = `media_files` 中 `file_path LIKE 'P/%'`（跨所有库、未软删）的下一级目录去重；文件 = 目录恰为 P 的项。
- 多个有路径包含关系的库在公共上级自然合并为单一树（`D:\1` 与 `D:\1\2` → `D: → 1 → 2`）。
- 排序由后端 `sort` 参数化（name/size/type/time）。
- `file_path` 真源不变、库注册不变；本决策只改「浏览时如何组织呈现」。

## 理由

- 贴合用户心智与「资源管理器」诉求：按真实路径浏览，库只是「注册了哪些根」，浏览不再被库边界割裂。
- 跨库前缀聚合让包含关系自然成树，无需额外维护库间父子关系。
- 复用现有 `file_path` 索引与前缀查询（ADR-0037 已有的机制），改的是「是否按 library_id 收窄」与「顶层根怎么来」，不引入新存储/新机制。

## 后果

- 行为变更：同一路径现返回**跨库合并**结果（旧为单库）；既有 browse 测试更新到新语义（属预期内）。
- `DirInfo.library_id` 对子目录不再有意义（子目录可跨库），仅文件保留自身 `library_id` 供删除/下载等操作。
- `GET /api/library/browse` 的 `library_id` 参数退化为可选/忽略（导航按路径），新增可选 `sort`；响应结构不变（向后兼容）。
- 前端目录浏览重做为资源管理器布局（左树 + 地址栏 + 详情列 + 状态栏），移除全局页级面包屑。
- ADR-0037 状态改为「已被 ADR-0046 取代」，正文不动（ADR 不可变、只取代）。

## 备选方案

- **保留虚拟库根（ADR-0037）**：改动最小，但无法呈现库间真实路径包含关系、不满足「资源管理器 + 整盘浏览」诉求。落选。
- **库间显式父子关系表**：维护一张库包含关系表来拼树——多一处真源、与 `file_path` 易不一致，复杂且脆弱。落选（跨库前缀聚合用现成 `file_path` 即可，无需新表）。
- **仍按库下钻但前端拼接成树**：把跨库合并逻辑放前端——前端要拉多库数据自行归并，重复且低效，且分页/排序难统一。落选（后端按路径聚合更自然）。

# ADR-XXXX：运行期设置持久化采用 SQLite settings 表

## 状态
已接受

## 背景
后续能力需要运行期可改的配置项：回收站清理（FR-26）需要「每盘符回收站路径」，定时扫描（FR-28）需要「扫描周期」。这些配置必须运行期可改、重启后保留，且能被前端设置页读写。当前 `config` 模块只负责启动期从环境变量/配置文件加载端口、FFmpeg 路径等不可变项，不适合承载用户在运行期反复改写的业务配置。

## 决策
运行期设置以 SQLite `settings` 表（`models.Setting{Key, Value, UpdatedAt}`）作为唯一真源，按 key 读写键值；新增 `internal/settings` 服务封装读写，经 `GET /api/settings`（读全部）与 `PUT /api/settings`（批量 upsert）暴露给前端设置页。

## 理由
- 数据库已是元数据真源（ADR-0002，SQLite WAL），运行期可改的设置天然属于「数据」而非「启动配置」，放在同一数据库内一致且零新增依赖。
- 键值表足够简单，满足单用户少量配置项场景，不需要引入额外配置中间件（符合架构「简单优先」不变量，禁 Redis 等）。
- 与启动期 `config` 模块职责分离：`config` 管不可变的部署参数（环境变量优先），`settings` 管用户运行期改写的业务配置，避免把可变状态塞进只读配置。

## 后果
- 设置读写经数据库事务，批量写在单事务内原子完成，提交成功后再对外返回，保证一致性。
- 设置值统一以字符串存储；结构化配置（如「每盘符回收站路径」）以 JSON 字符串存于单个 key，由消费方按需解析；这要求消费方与设置页约定 key 名与编码格式（key 名以常量集中定义，避免散落魔法字符串）。
- 后续设置项只需新增 key 常量与设置页字段，无需改表结构。

## 备选方案
- **新增独立 YAML/JSON 配置文件**：需自行处理并发读写、文件锁与原子写，且与既有数据库真源割裂；不采用。
- **塞进启动期 `config` 模块**：`config` 为启动期只读加载，承载运行期可变状态会污染其职责并难以做事务一致写；不采用。

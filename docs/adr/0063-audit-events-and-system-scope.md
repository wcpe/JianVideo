# ADR-0063：审计事件可靠性与系统级作用域

## 状态
已接受

## 背景

v2 把 Space 定为资源、权限、任务、审计和 AI 可见性的边界。ADR-0056 要求业务资源带 `space_id`，ADR-0055 要求任务带 Space 归属。但 P2 还会出现工具下载、硬件探测、迁移、全局配置诊断等系统级操作，它们不是某个 Space 的业务资源，却同样需要被任务中心展示或被审计日志追踪。

同时，审计事件不能只是“业务成功后尽力补写日志”。对于配置、库、媒体、任务、缓存、迁移等必须审计的动作，如果审计缺失仍提交业务变更，后续多用户、安全与恢复能力会失去可信追溯基础。

## 决策

审计事件采用 SQLite `audit_events` 表作为操作事件真源。必须审计的业务变更与审计事件必须在同一 SQLite 事务中提交；业务代码通过 `RecordTx` 写事件，或在同一事务内写入审计 outbox 记录。审计写入失败时，必须审计的业务事务整体回滚。

系统级作用域统一采用显式 `scope` 字段：

- `scope=space`：Space 资源相关事件或任务，`space_id` 必须非空。
- `scope=system`：全局系统操作，例如工具下载、硬件探测、数据库迁移、全局诊断，`space_id` 必须为空。

Space scoped 查询默认只返回 `scope=space` 且匹配 `space_id` 的记录；`scope=system` 只在系统管理上下文中查询。系统级任务与系统级审计事件沿用同一 scope 语义。

事件与任务的可靠性边界：

- 异步流程可以用于导出、展示缓存、通知或后处理，但不能作为审计真源的补写机制。
- 如果采用同事务 outbox，outbox 行本身就是已提交的审计真源；后续投递失败不得影响已经提交的事件事实。
- 失败业务不得写成功事件；可以写失败事件，但必须准确表达失败状态。

保留与清理：

- P2 不提供普通用户删除审计事件能力。
- 审计事件不属于缓存资产，不能被普通缓存清理删除。
- 保留期、导出、签名链或外部 SIEM 接入需要另写 ADR 或后续规格。

脱敏：

- 审计 `before_json`、`after_json`、`metadata_json` 只记录必要字段或资源摘要。
- 密码、令牌、JWT、SMB 凭据、代理 userinfo 等敏感值必须在写入事件前脱敏。
- 日志与审计 API 复用同一脱敏策略。

## 理由

- 显式 `scope` 能让 Space 资源与系统操作同时可追踪，避免把全局事件硬塞进默认 Space 造成语义污染。
- `scope=system + space_id NULL` 比固定默认 Space 更清楚，能防止系统任务被 Space 列表误判为用户资源。
- 同事务审计能保证“业务事实”和“审计事实”同时存在，满足后续权限、安全、恢复和问题追踪的地基需求。
- 不把审计事件交给普通缓存清理，能避免用户误删关键追溯记录。
- P2 先建立可靠事件模型，签名链、导出和保留期策略可以在有真实使用需求后再扩展。

## 后果

- 必须审计的写操作需要拿到事务上下文或同事务 outbox，接口设计会比普通日志调用更严格。
- 审计失败会阻止对应业务变更提交，部分 API 需要新增错误路径测试。
- 所有任务和审计查询都要理解 `scope` 字段，Space scoped 页面默认不展示系统级记录。
- FR2-037 与 FR2-040 需要共同采用本 scope 语义；FR2-022、FR2-056、FR2-017 等系统级操作也要按本 ADR 接入。
- 系统事件不归入默认 Space；若后续要改变该口径，必须新增 ADR 取代本决策。

## 备选方案

- **业务提交后异步补写审计**：请求路径简单，但进程崩溃或补写失败会留下无审计的业务事实，被否。
- **所有事件都挂默认 Space**：查询实现简单，但系统操作会污染默认 Space，且未来多用户下语义不清，被否。
- **按动作类型各自定义作用域字段**：局部灵活，但任务、审计、API、前端会出现多套过滤语义，被否。
- **立即实现不可篡改签名链**：安全性更高，但密钥、轮换、导出和验签流程未定，超出当前地基范围，被否。

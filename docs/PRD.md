# 产品需求文档（PRD）：JianVideo v2 自托管视频素材与 AI 媒体中心

> 本文是从 `v0.21.0` 起生效的 v2 需求真源。旧版 `v0.20.x` 之前的长表与周任务式分期已归档到 [`docs/archive/PRD-v0.20-history.md`](archive/PRD-v0.20-history.md)，旧分期全部废弃，只作为历史查询，不再作为后续排期依据。

## 1. 背景与目标

JianVideo v2 从“轻量单用户家庭媒体库”升级为“自托管优先的视频素材与 AI 媒体中心”：以视频媒体为主，面向重度素材库、家庭/小团队空间、转码队列、HLS 预览、AI 索引、审核流和多端使用。产品仍坚持一体化部署优先，但容量目标按重度素材库设计：单实例目标管理 500 万到 1000 万媒体资产，支持 10 到 50 个用户。

核心目标：

- 自托管优先：1.0 核心路径不依赖官方云账号、官方中继、官方托管存储或官方 SaaS 多租户。
- 视频优先：优先做好存储库索引、视频 HLS 预览、转码任务、转码队列、播放与审核流；相册不再作为 1.0 主线能力。
- 高密度渲染优先：从首个 mock UI 开始引入 PixiJS 作为大规模媒体网格/时间轴的核心渲染方案，必须测试 100 万以上素材的前端渲染性能。
- 后端索引优先：数据库索引、分页、排序、筛选、任务队列和 AI 索引从 P0/P1 就按 500 万到 1000 万资产目标设计和压测。
- 工具链先冻结：P0 与 P1 之间先完成 apps/packages 工作区、pnpm/Turborepo、Vite/React Router/TanStack Query/Zustand/react-i18next/MSW 和最严静态检查门确认。
- AI 是核心能力但不能绑死实现：模型、索引、推理节点和重建策略必须可替换、可审计。
- Space 是策略边界：权限、删除、同步、AI 可见性、分享、审计和写回都必须按 Space 执行。
- 支持 Web、Desktop、Android、iOS、Android TV 和安卓车机，优先支持一体化部署。

## 2. 用户与场景

| 角色 | 主要目标 |
|---|---|
| 视频素材用户 | 管理硬盘/NAS/工作盘中的大量视频素材，快速预览、筛选、转码、标记和审核。 |
| 家庭/小团队维护者 | 用一台自托管实例服务 10 到 50 个用户，按 Space 管控可见性、删除、分享和审计。 |
| 创作/剪辑用户 | 通过 HLS 预览、外部播放器、转码队列和 AI 检索快速找到可用素材。 |
| AI 工作流用户 | 对人脸、OCR、对象/场景、视频内容理解、向量语义搜索、AI 去重与审核流有可替换、可审计的本地/自托管需求。 |
| 多端使用者 | 在 Web、Desktop、移动端、电视和车机端访问同一套素材库能力。 |

## 3. 产品原则

- **自托管优先**：核心路径不依赖官方云，不把官方账号、官方中继或官方 SaaS 当基础能力。
- **原文件安全优先**：任何删除、写回、迁移和同步都必须可追溯、可恢复或明确提示风险。
- **视频媒体优先**：转码、预览、任务队列、播放器、审核和 AI 视频理解优先级高于相册和照片娱乐体验。
- **空间边界优先**：权限、删除、同步、AI 可见性、分享、审计、写回都必须挂到 Space，不做全局模糊权限。
- **可重建数据不可信**：缩略图、代理文件、索引、AI 中间结果可删可重建；原媒体、sidecar、事件日志和人工元数据才是可信源。
- **AI 可替换可审计**：模型、向量索引、推理节点和重建策略必须能替换、重跑、审计和回滚。
- **性能证据优先**：首个 mock UI 就要跑 100 万素材级 PixiJS 渲染；后端索引要跑 500 万到 1000 万资产级查询/写入压测。

## 4. 范围与非目标

范围内：

- 本地/SMB/NAS/工作盘存储库，扫描、索引、元数据、sidecar、可信事件日志。
- 视频 HLS 预览、转码任务、队列、状态、失败重试、外部播放器和审核流。
- PixiJS 高密度媒体网格/时间轴/预览层，wiki UI 博物馆和 mockup 先行。
- Space、用户、权限、分享、审计、删除恢复、AI 可见性和写回边界。
- 人脸、OCR、对象/场景识别、向量语义搜索、视频理解、AI 去重和审核流。
- Web、Desktop、Android、iOS、Android TV、安卓车机，多端复用同一 API、主题和媒体能力。

非目标：

- 1.0 不做官方云账号、官方中继、官方托管存储或官方 SaaS 多租户依赖。
- 1.0 不把 Web 上传作为核心路径；入库以存储库扫描为主。
- 1.0 不优先做传统相册、照片娱乐回忆流或社交分享。
- 不做分布式集群转码作为默认部署；单实例重度素材库先达标。
- 不把 PixiJS、AI 模型或数据库扩展写死为不可替换实现；必须保留替换和重建路径。
- 1.0 不做移动端离线下载、SSO/OIDC 登录、Web 上传主入口和联网元数据刮削；均列为 1.x 候选，先记录不实现。

### 4.1 v2 能力地图

| 能力域 | v2 要覆盖的能力 | 边界 |
|---|---|---|
| 存储库与索引 | 本地/SMB/NAS 存储库、增量扫描、数据库索引、sidecar、事件日志、路径安全 | 不以 Web 上传为主入口 |
| 视频预览与转码 | HLS 预览、转码任务队列、失败重试、任务状态、外部播放器、代理文件重建 | 不让匿名分享触发高成本转码 |
| 播放体验 | 逐帧/阶梯步进、进度条悬停预览、字幕与音轨、变速与 A-B 循环、画中画、投屏 | 播放核心先在 Web 达标并封装为 player-core，多端复用同一核心 |
| 元数据与可信编辑 | 文件自带元数据解析、本地离线影视推断、系统内编辑与危险回写、图片高级编辑覆盖、视频粗剪导出 | 默认只改数据库不动原文件；不联网刮削（留 1.x） |
| 高密度前端渲染 | PixiJS 媒体网格/时间轴、100 万级 mock UI、缩略图/视频预览纹理管理 | 不在 1.0 核心滚动热区依赖重 DOM 卡片堆叠 |
| Space 与安全 | Space 权限、删除、分享、审计、AI 可见性、同步和写回边界 | 不做全局模糊权限 |
| AI 索引与审核 | 人脸、OCR、对象/场景、视频理解、向量语义搜索、AI 去重、审核流 | 模型和索引必须可替换、可审计、可重建 |
| 多端交付 | Web、Desktop、Android、iOS、Android TV、安卓车机，一体化部署优先 | 不让各端复制一套产品逻辑 |
| 架构与工具链 | `apps/*` + `packages/*` 工作区、pnpm/Turborepo、Vite、React Router、TanStack Query、Zustand、react-i18next、MSW | P0.5 冻结后再进入 P1 实现 |
| 运维与质量门 | 初始化向导、设置、诊断、队列监控、Benchmark、E2E、发布包质量门 | 不引入官方托管运维平台作为核心依赖 |

### 4.2 非功能需求

| 类别 | 要求 |
|---|---|
| 前端渲染性能 | 首个 mock UI 必须用 PixiJS 验证 100 万素材级网格/时间轴滚动。React DOM 壳层只承载壳层、表单、面板和 wiki UI 博物馆，不进入核心滚动热区。 |
| 后端索引性能 | P0/P1 必须定义并测试 100 万、500 万、1000 万资产级查询、分页、排序、筛选、任务入队和索引写入口径。 |
| 原文件安全 | 删除、写回、迁移、同步必须有事件日志；不可恢复操作必须显式确认；可恢复路径优先于直接破坏源文件。 |
| 数据可信度 | 原媒体、sidecar、事件日志、人工元数据是可信源；缩略图、代理文件、向量索引和 AI 中间结果必须能删除重建。 |
| AI 可审计 | AI 结果要记录模型、版本、输入范围、Space、重建批次和人工确认状态；人工元数据优先级高于 AI 推断。 |
| 多用户边界 | 10 到 50 用户按 Space 隔离权限、AI 可见性、分享、删除和审计；不允许跨 Space 隐式泄露。 |
| 多端一致性 | 多端共享 API client、主题、权限模型和媒体能力；TV/车机优先浏览、预览和播放，不承载复杂管理。 |
| 静态检查 | Go、TypeScript、Rust、Kotlin、Swift 均按目标端最严档定义质量门；实际启用某端语言前必须先接入对应 lint/typecheck/test/build 任务。 |
| 数据迁移 | v0.20 既有 SQLite 数据、配置、媒体库路径和用户数据升级到 v2 必须有版本化迁移、回滚说明和演练数据。 |
| 备份与恢复 | 可信源中的 sidecar、事件日志、人工元数据、配置和数据库必须有导出、备份、恢复与灾难恢复策略；原媒体不被隐式搬迁。 |
| 国际化与无障碍 | 多端文本资源必须可国际化；Web 主端至少满足键盘可达、焦点可见、对比度和触控目标的基础无障碍验收。 |
| 数据层可移植 | 第一版仅用嵌入式数据库（SQLite）；数据访问层保留未来接入外部 PgSQL 的抽象，不把嵌入式实现硬绑死；真正接入外部库前先写 ADR。 |
| 前端主线程不阻塞 | 解析、虚拟化、缩略图/纹理等重活一律 Worker 化或进后台任务队列；遵守 fr2-003 的“10s 窗口内无 >200ms 长任务”门，网页不因后台工作卡顿。 |
| AI 默认关闭 | 未配置模型与向量库时 AI 能力整体不可用；只有配置齐备并显式启用后才开放，且结果按 Space 可见性隔离。 |
| 安全基线 | 自托管暴露公网时提供 HTTPS/反向代理指引、登录防爆破、会话与设备管理；敏感项不入库走环境变量。 |

### 4.3 关键技术风险

| 风险 | 当前处理 |
|---|---|
| SQLite 承载 500 万到 1000 万资产与 10 到 50 用户的上限 | P0/P1 通过 FR2-003 Benchmark 验证；如达不到目标，必须另写 ADR 决定数据库或索引策略。 |
| PixiJS 100 万素材渲染热区 | P1 先用 mock UI 和 Benchmark 验证，再进入正式浏览器实现。 |
| v0.20 数据升级到 Space 与新索引模型 | P2/P4 前必须补迁移规格，禁止破坏历史库。 |
| AI 中间结果可信度 | AI 结果默认可重建，人工元数据、sidecar 和事件日志优先。 |
| 匿名分享触发高成本转码 | P4 分享设计必须禁止匿名路径触发高成本转码或 AI 任务。 |

## 6. 版本线与分期

分期是产品路线，不是周任务列表。每一期对应一条 `MAJOR.MINOR.PATCH` 版本线：同一 `MINOR` 下的所有 patch 都属于同一阶段，例如 `0.21.0`、`0.21.1`、`0.21.2` 都属于 P0。`PATCH` 按需要递增，不设固定上限。

`1.0.0` 之前属于 `0.y.z` 预稳定阶段；三段版本号从一开始就使用，但严格 SemVer 语义从 `1.0.0` 后开始执行：`1.0.1` 表示兼容修复，`1.1.0` 表示兼容新增功能，`2.0.0` 表示破坏性变更。预发布使用 `1.0.0-rc.1`、`1.1.0-beta.1` 等格式。

完整路线图见 [`docs/ROADMAP.md`](ROADMAP.md)。

- P0 必须补齐旧能力矩阵，明确 `v0.20.x` 已交付能力在 v2 中是保留、重做、推迟还是废弃；当前规格见 [`docs/specs/fr2-004-compatibility-matrix.md`](specs/fr2-004-compatibility-matrix.md)。

- 架构不变量必须包含 v2 过渡说明，避免当前代码真貌约束与 P0.5 目标 ADR 混用。

- 当前代码行为不因文档重构改变。

## 8. SDD 执行规则

- **PRD**：只放产品目标、功能登记册、阶段路线和期级验收。
- **ROADMAP**：只放阶段版本线、阶段目标、进入/退出条件和质量门。
- **specs**：放具体功能的设计、任务拆分、测试与验收。一个可独立开发的非平凡功能对应一个 spec。
- **ADR**：放长期架构决策，例如 PixiJS 渲染方案、Space 权限模型、AI 索引策略、数据库索引策略、端形态。
- **ARCHITECTURE**：只描述当前系统真貌；目标架构先放 ADR/spec，代码迁移完成后再同步 ARCHITECTURE。
- **CHANGELOG**：只记录用户可见变更与发版变更，不承载开发计划。

## 9. 术语表

| 术语 | 含义 |
|---|---|
| Space | v2 的策略边界，权限、删除、同步、AI 可见性、分享、审计和写回都按 Space 执行。 |
| 可信源 | 原媒体、sidecar、事件日志和人工元数据，不能被可重建缓存或 AI 中间结果替代。 |
| 可重建数据 | 缩略图、代理文件、索引、向量、AI 中间结果，可删除并按可信源重建。 |
| PixiJS 渲染热区 | 用 PixiJS 承载 100 万级媒体网格/时间轴滚动，React 只承载壳层和控制面板。 |
| HLS 预览 | 为视频素材生成或复用可快速预览的 HLS/代理片段，服务浏览、审核和多端播放。 |
| AI 可替换 | 模型、索引、推理节点和重建策略不是产品契约本身，必须能替换和审计。 |
| 一体化部署 | 默认用一个自托管实例承载 API、媒体索引、任务队列、前端资源和端连接能力。 |
